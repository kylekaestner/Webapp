# CrewSync: NetJets

Current behavior only. Past bugs and why things were built this way: `CLAUDE_HISTORY.md`.

## NetJets manual tracking (`parser_type: 'manual_netjets'`)

NetJets publishes no exportable schedule feed at all — a manual-entry pilot type built around how NetJets pilots actually work: home-based, tail-locked for a whole tour, on a rotation. One real account: `mack` / Mack Kraus (base/home both DFW).

**Tail → ATC callsign rule**: `EJA` + the full numeric run of the tail, no truncation (`ejaFlightNumber(tail)` server-side, `deriveCallsign()`'s `EJA` branch client-side — both just strip non-digits). **`EJA####` is only used in the lower 48 + Canada.** Anywhere else (Caribbean, USVI, etc.) NetJets files under the bare tail number `N####QS`. `_getOnDutyNetjetsPilots()` returns both (`callsign`, `tailCallsign`), both are registered with the SWIM feeds, and `_pollNetjetsLegCreation()` merges both into one leg list. Each leg keeps the callsign it was filed under as its `flight_number`, which live tracking polls (`normalizeFlightNum()` leaves `N22QS` intact). Confirmed 2026-11-02: N22QS flew ORL→TISX as `N22QS` while its EJA22 plans for that afternoon were cancelled.

**Exposed in the admin dropdown only** — never in `join.html`'s public self-signup. `AIRLINE_OPTIONS` has a real `EJA` entry (`parser: 'manual_netjets'`, `needsIcs: false`) in both the admin edit-user modal and the self-service My Info modal.

**Home-based**: `pilots.base === pilots.home_airport` for this pilot type, so `buildGroundPeriods`'s commuter branch never triggers.

**Duty rotation + per-tour tail.** `pilot_duty_rotation(pilot_id, anchor_date, days_on, days_off, effective_from)` and `pilot_tour_tail(pilot_id, tour_start_date, tail, start_airport)` (`UNIQUE(pilot_id, tour_start_date)`, upserted). `GET /api/pilots/:key` returns `rotation_history`/`tour_tails`. `PUT /api/pilots/:key/rotation` / `.../tour-tail` (admin-or-self). Resolution: `_resolveRotationAt()` → most recent rotation row still effective; `_tourStartDateFor()` → modular-arithmetic day-1 of the on-duty tour containing a date, or `null` if off-duty/unconfigured; `_tourTailFor()` looks up the saved tail for that tour start. The pilot just picks any known Day-1 date + Days On/Off — no external line/family mapping needed for the base rotation case.

**Off Days integration.** `_isOffDutyGeneric(pilotKey, dateStr, pilotFlyingDates)` — off only when there's neither a real logged segment nor the rotation saying on-duty. Wired into `renderCommonOffSection()`, `renderOffDayCalendar()`, `showOffDayDetail()`. Falls back to pure segment-based when no rotation is saved yet.

**Self-service UI.** `#my-info-netjets-section` (Days On/Off + Anchor Date + Save; numeric tail input + Save, keyed to today's resolved tour start). `_refreshMyInfoNetjetsStatus()` shows current status. Add Flight modal pre-fills Tail#/Flight# from the saved tour tail.

**Auto-creating legs.** SWIM-first: the derived `EJA` callsign is fed into `setRelevantCallsigns()` proactively every poll cycle via `_getOnDutyNetjetsPilots()`, merged in before the main scheduled-flight relevance computation (NetJets legs have no `departure_time` to drive that query otherwise). `_pollNetjetsLegCreation()` materializes **every known leg** from a per-leg store (`tfdm.getAllLegs()`/`tfms.getAllLegTimes()`, both disk-persisted and scoped to EJA callsigns only) rather than tracking just "the current" leg — real NetJets callsigns routinely carry 2+ concurrently-filed legs, sometimes spanning today and tomorrow. Matching across polls is fuzzy (an estimated time can legitimately drift poll to poll), not an exact key. `isParkedForOrigin()` (NetJets-specific) avoids the generic `isParked()`'s single-slot-per-callsign confusion when two legs on the same tail are both tracked.

**Leg matching/filtering rules in `_pollNetjetsLegCreation()`** (EJA+tail = one physical aircraft, so there's no "different flight, same callsign" ambiguity):
- Origin/dest come from TFMS's `depArpt`/`arrArpt` message attributes (`attrAirport()`, tfms.js) as a fallback when no route string is present (~90% of NetJets-relevant TFMS traffic). Airports are normalized via the shared `norm3Airport()`, also applied to manual edits of a `manual_netjets` pilot's segments. **It strips the K only when the 3-letter code means the same airport** (`_kCodeCollides()`, over 50 km apart = collision): KCQF stays `KCQF` because CQF is Calais, and KBKV stays `KBKV` (BKV is in China). The app's `normApt()` uses the same rule (`_prefixCollides()`). A blanket "prefer K" lookup was rejected because HND, PVG, DUB, PUJ and GCM have US K-code namesakes. Renamed airports newer than the bundled data are aliased on both sides (`_AIRPORT_RENAMES`: KPBI → KDJT).
- **`_collapseSameDepartureLegs()`**: TFDM can hold several versions of one departure at once (EJA23 11/3: SAT→E38, SAT→KPEQ, SAT→ZZZZ, alternating). They're collapsed to one per origin + departure instant, both before the chain is built and before rows are touched. The kept destination is the one TFMS proves was flown, else TFMS's most recently updated plan. `ZZZZ`/`XXXX` (the flight-plan placeholder for a field with no ICAO code) is never treated as an airport.
- **Route `/HHMM` arrival time** (`leg.routeEta`, tfms.js): the 4 digits after a route's destination are the elapsed time in a plan sent before departure (572/627 fit), and the clock arrival time in UTC in an amendment sent after departure (507/559 fit). It's used right after TFMS's direct `eta`.
- `_findExistingNetjetsLeg()`: a dest mismatch against an open row is still the **same leg** when both share an origin at nearly the same departure instant (15min tolerance, separate from the 6h refine tolerance) — covers diversions (`isDiversion`) and NetJets inserting/removing a stop before departure.
- **Chain-consistency filter**: once the tail has really departed an airport (`REALLY_DEPARTED_RE`, taxi-out or later), any still-FILED/SCHEDULED candidate arriving at that airport at or after that departure is a stale plan and is skipped (or `auto_leg_cancelled`-marked if already created). Earliest confirmed departure per origin is used, so a real later return visit isn't touched.
- **TFMS-only legs** (`_tfmsOnlyFlownLegs()`): TFDM only covers towered airports, so a leg at an untowered field (EJA492's 27K→LBE) never appears in `tfdm.getAllLegs()`. Such a leg is added from TFMS only with real-movement proof: `departedAt`/`arrivedAt`/`tracked`, which tfms.js sets on `departureInformation`/`arrivalInformation`/`trackInformation`. It's added only when TFDM has no record of that departure at all (same origin within 1h). It is **not** added on `etdType: ACTUAL` alone, since some fleet legs are ACTUAL and also cancelled. **In advance**: the earliest still-filed, uncancelled TFMS plan departing the dest of the latest leg already on the schedule is also added (`SCHEDULED`). That latest leg can be any TFDM leg, since those are created as soon as they're filed, or a proven TFMS leg. A TFDM leg whose matching TFMS plan is cancelled is never used as that starting leg, since TFDM can keep it at SCHEDULED. The chain starts at the last leg that really moved (else the first filed TFDM leg) and walks forward one airport at a time, up to 12 steps, taking the next departure from wherever it's filed, TFMS or TFDM. Anchoring on the latest TFDM leg used to skip TFMS-only legs in between (EJA492 jumped to HOT→CLT and skipped DJT→CQF→HOT). A plan from any other airport waits until the tail actually gets there. Used by both the leg creator and the Lookup's Resolved table. An in-advance leg (`inAdvance`) that's 3h+ past departure with no departure/track/arrival event is never created, or `auto_leg_cancelled` if it was: 11% of filed plans are dropped with no cancellation message.
- **Research-log baselines (fleet, 2026-10-30 → 11-03, 2,686 real flights)**: 53% of real legs are TFMS-only (no TFDM). Plans are filed ~16–18h ahead (12% ≥18h, none ≥24h). 31% of filed plans never fly (20% cancelled, 11% silently dropped). Median departure is +7min vs filed (p90 +54). Tails fly near-continuously across crew changes (only 30/536 idle ≥36h), so tours can't be inferred from aircraft data and must come from the pilot.
- **Deleting an auto leg** sets `auto_leg_cancelled=3` and keeps the row, because a leg still filed on the tail would be rebuilt on the next poll. The values: 1 cancelled by the feeds, comes back if it really flies. 2 left behind by a last-leg pick, comes back with "Staying on this aircraft". 3 deleted by the pilot, stays off.
- **`block_minutes`** only comes from a real arrival. An estimate clears it, and the app works block out from the row's times. `.netjets_route_durations_v2.json` holds one count per real arrival; on first run it collapsed the old file's per-poll counts to one entry per route, keeping each average.
- **`_tfmsPlanFor()`** picks a leg's TFMS plan for the creator and the Lookup: same airports, closest departure.
- **A refile isn't acted on yet**: `tfms.js` logs `new GUFI after cancellation`. Check those lines against what flew before restoring a leg on a refile. TFMS keeps one plan per airport pair, starting fresh when a filing is 6h+ away and the old flight is over.
- **Cancelled plans** (end of each poll): a row the loop didn't reach is `auto_leg_cancelled` when its TFMS plan is cancelled, since a cancelled plan can drop out of TFDM and the chain while the row stays. Flown and hand-edited rows are left alone. A cancelled leg that then shows real movement is restored. A plan filed again doesn't restore it on its own, because TFMS keeps the cancelled flag until the aircraft moves.
- **Origin-side cleanup** (end of each poll): an unflown, unedited auto row that no current candidate matched is `auto_leg_cancelled` once the tail really departs that same airport on a different leg (more than 15min apart, within 12h). This mainly catches an in-advance leg that never flew.
- Time priority: `etd`/`eta` over `airlineOutTime`/`airlineInTime` — NetJets doesn't feed real OOOI, those fields just freeze at the original plan.
- **Row times follow the flight, not the filing** (`_netjetsRowTimes()`): before departure a row keeps its planned time so a slipping ETD shows as `DELAYED · ETD`, and only a 3h+ change (a re-plan) moves it. Once flown it takes the real departure, then the real arrival: `eta` when `etaType` is `ACTUAL`, else a non-estimated `timeOfArrival`, else `arrivedAt`. `arrivedAt` is only when the message reached us, up to 6 minutes after landing. With none of those, as on a leg into an untowered field, the estimate is used, but it stops updating once the leg is complete and can't land after the tail's next departure from that airport. Grid, list and map all read the row. The grid poller refetches 20s after a leg goes live or parks (`_refetchNetjetsTimes()`).

**Cancellations** (`segments.auto_leg_cancelled`): set on a TFMS `flightPlanCancellation` or by the chain filter. The row stays in the DB for research, but it's excluded from every pilot-facing view (grid, list, day detail, both maps, the next flight banner, layover labels, Wrapped, `inferAwayLayovers`, Crossings/Off Days).

**Leg state is per leg, like an airline flight number** (the root of the map/grid mixups): airline legs each have their own flight number, so per-callsign evidence is per-leg for free, but one NetJets callsign flies every leg of the day. The app keys NetJets evidence by **callsign + departure airport**: `parkedKey(cs, depApt)` for `_confirmedParked`, and `isFlightStillActive(…, csig, depApt)`. A caller without the airport just loses the parked short-circuit and never marks the wrong leg done. The day map sends every NetJets leg separately (`njlegs=callsign~origin~arrival`), and `/api/flight-status` answers each from TFMS's per-leg store (`perLeg["callsign~origin"]`: airborne = ever flew, parked = arrived, times = that leg's own, live only for the leg actually being flown). `_legState(…, origin)` uses that answer when present. Single-leg requests (the grid poller) get the same per-leg treatment through `njLegOf`. Airline legs are unchanged.

**One answer for "which leg, and is it done"** (server.js, beside `_tfmsLegArrived`). Everything about a NetJets leg goes through these, and `getAllLegTimes()` returns copies, so legs are compared by `.key`, never `===`:
- `_njLegFor(cs, origin, arrMs)`: TFMS's record of one scheduled leg (closest arrival, uncancelled preferred, nothing over 12h off).
- `_njLegDone(t, legs, now)`: real arrival, or a later leg has moved, or past ETA +30min with TFMS silent 15min. TFMS doesn't always send an arrival (EJA23 E38→OKC went quiet 11min after departure), and without this the leg stayed "being flown" and blocked every later leg.
- `_njFlyingLeg(cs, now)`: the leg the aircraft is on now.
- `_njLegGate()` decides without a position: done → `{found:false, parked:true, notThisLeg:true}`, another leg being flown → `{found:false, notThisLeg:true}`. Runs before the per-callsign parked flag and cache in `/api/live-position`. `notThisLeg` answers are never written to `_liveCache`.

**Later legs get no callsign evidence on the day map**: `/api/flight-status` `perLeg` only covers legs near now. `_legState()` used to fall back to the callsign for the rest, so with the aircraft live every later leg read as active and took over the tracker, and the day's last leg held the plane (Mack's LAS→VNY while flying AFW→VNY). A NetJets leg with no `perLeg` entry and a departure still ahead now has no evidence at all. A running APU doesn't hold a leg open either: `_njLegDone()` ends it on arrival, a later leg moving, or ETA + 30 minutes with TFMS silent, not on the position stopping.

**Live position is per leg**: `fetchLivePosition(cs, origin, arrMs)` wraps `_fetchLivePositionRaw()` for NetJets. A not-yet-moved leg on the ramp gets `_njRouteOnly()` (filed route, no position), since that position and any parked flag are the previous leg's. A last fix that's low (<1500 ft), over 2min old and near the ETA reads as landed. With no origin given (the background poller) it answers for the leg being flown: the flat SWIM record can be two legs at once (origin CQF, route HOT→CLT), and caching that put the next leg's route on the current one. A cached NetJets answer must name its origin. `resolveRouteWaypoints()` only uses TFMS's trajectory and TFDM's runway when they aren't known to be for another leg, since both are per callsign.

**A leg's route waits for the leg before it**: `_earlierLegOpen()` holds the preview at all three map sites. `startLiveTracking()` tears down whatever that callsign had, so only one leg per callsign can be on the map.

**A next leg's scheduled time doesn't end a NetJets leg**: `_hasNewerLegStarted()` returns false for these callsigns. It only reads the schedule, and a cancelled or delayed next leg marked the flown leg completed mid-flight.

**NetJets legs are never "landed early"**: airborne/trail evidence is per callsign, so a parked aircraft's next leg inherited it and no position read as signal lost after landing (EJA492 HOT→CLT flagged on the ramp, CQF→HOT mid-flight). `_isNetjetsLeg` in `startLiveTracking()` skips the miss-based endings, and stored flags for these callsigns are ignored. They end on `d.parked`, or past arrival.

**TFMS leg key has no date** (`origin>dest`): `processLegTimes()` starts a fresh entry when a filing is 6h+ from the stored departure and the old flight is over, otherwise a repeat of a city pair inherits the old departed/arrived evidence.

**No ADS-B is the normal state before departure.** `fetchAdsbPosition()` rejects then, so `_fetchLivePositionRaw()` holds that error until after the filed-route return. An unguarded await skipped it and no leg got a preflight route. For airlines the route is only returned if the callsign hasn't flown yet, so a landed flight still reaches the error path.

**A filed route attaches to a leg, it never makes one.** Leg creation (`_pollNetjetsLegCreation()`, from TFDM/TFMS) and route display are separate. `swim.js` keeps routes in `_legRoutes`, keyed `ORIGIN>DEST`, EJA/`N####QS` only, persisted, alongside the flat `_latest[cs]`. `getRouteForLeg(cs, origin, dest, arrMs)` returns one only when origin and destination match the scheduled leg and it was sent around that flight (48h before arrival to 6h after, since the pair recurs). No match means no route, never the flat record. The app sends `origin`, `dest` and `arrMs` on every `/api/live-position` call. Separately, `fetchLivePosition()` falls through to ADS-B whenever SWIM has no **live** position, which matters for oceanic legs, and the filed route is carried forward either way.

**Research mode (temporary, `NETJETS_RESEARCH_MODE` in tfdm.js/tfms.js/swim.js)**: every `EJA####` **and** bare tail-number `N####QS` callsign is treated as relevant fleet-wide (NetJets files under the tail outside the lower 48 + Canada). Cheap substring/regex pre-filter only, never a per-tail loop. Research callsigns get 7-day per-leg retention (`LEG_STALE_MS_RESEARCH`/`LEG_TIMES_STALE_MS_RESEARCH`) instead of 48h, since a completed leg's `lastMsg` stops updating. **These constants must stay declared above each file's load-from-disk block** — declared later, they sit in the TDZ when the restore runs, the swallowed ReferenceError silently skips the restore, and the next save wipes the persisted cache.

**Existing-row lookup spans every tour** (`auto_leg_key LIKE '<callsign>|%'`), so a changed tour start can't hide an already-created row and duplicate it.

**One row per leg**: only one `_pollNetjetsLegCreation()` pass runs at a time (the 15s poller doesn't wait for the last pass), and the insert refuses an `auto_leg_key` that already exists.

**Restart-safe by construction.** `auto_leg_key` (format `<callsign>|<tourStartDate>|<legNumber>`) on the `segments` row is the actual source of truth — `_pollNetjetsLegCreation()` queries fresh every call, no persisted in-memory cache.

**Resolving timing data for a leg**, in priority order: TFDM's parsed per-flight origin/dest (most authoritative) → TFMS's filed route string (`routeDest()`, local mirror of `routeOrigin()`) → reverse-geocoding the last known ADS-B/STDDS position (`_findNearestAirportCode()`) once a leg looks landed with no SWIM destination ever reported. `block_minutes` is a plain UTC diff (TFMS's `processFlightTimes()` already normalizes every time field to real UTC-with-`Z` strings — `pilotUsesUtc()` auto-detects this, same convention as Kyle's segments). An inconsistent arrival-before-departure value is corrected to `arrival_time = departure_time` (a neutral placeholder), never left `NULL` — several places in app.html assume a `type='flight'` segment always has both times.

**ETA placeholder for a leg with no real timing data yet** (never written to `block_minutes`, which comes only from a real arrival time; the borrowed-block-time lookup only uses real schedule rows, `auto_leg_key IS NULL`; estimates over 12h are discarded as bad coordinates), priority order: NetJets' own real average duration for that exact city pair from genuinely completed legs → any other tracked pilot's real scheduled `block_minutes` for the same city pair (`idx_segments_route` keeps this off a full table scan) → great-circle distance at an assumed 420kt cruise. `block_minutes` is never written from the estimate itself, only from real evidence.

**`start_airport` is informational, not a hard gate** — a mismatch between the saved starting airport and the aircraft's real position no longer silently blocks leg creation; nothing checks it, since the old hard-reject's failure mode was indistinguishable from "nothing's happening."

**A human's manual correction is never silently overwritten.** `segments.auto_leg_edited` is set unconditionally by the existing segment-edit endpoint — once a human touches an auto-created row, `_pollNetjetsLegCreation()` goes permanently hands-off on that row's fields, only reading `arrival_airport` back out as the next leg's informational context.

**Tour modal (`#netjets-tour-modal`)** — the per-tour tail/start-airport editor, opened from an "Edit Tour" button on the day-detail sheet (any on-duty day, on your own schedule, or on any pilot's as admin) or from the reminder. It edits `_netjetsTourModalPilot`, set on open, and names that pilot when it isn't you. **Mid-tour tail swap**: `PUT /tour-tail` detects a changed tail for an active tour and takes the new `start_airport` as given. `_closeOutTourLegs()`, also used by Reset, cancels legs under the old callsign that haven't departed and marks the rest complete. **Leaving this aircraft**: a pilot can name their last leg on the tail ahead of time, or after the fact, because the list includes flown legs from yesterday on (`PUT /tour-tail/last-leg`, stored as `pilot_tour_tail.last_leg_id`). Later legs get `auto_leg_cancelled=2`, which behaves like cancelled but is what "Staying on this aircraft" restores, and the poller skips anything departing after that leg until a new tail is saved. A new tail entered before that leg is complete is held in `next_tail`, and `_netjetsLegCreationPass()` switches to it once the leg lands, with the arrival as the new start airport. Before this, swapping early would have cancelled the leg still being flown. `_openCommuteForTour()` jumps from the modal into Add Flight → Commute with the arrival pre-filled from Starting Airport (the deadhead-to-the-jet shortcut).

**Joining**: `/join` offers NetJets (Beta), which saves `parser_type='manual_netjets'`, `airline_code='EJA'`. Step 2 (`method: 'netjets'`) asks for the schedule and line or CC program, saved through the same `PUT /rotation` as My Info (`saveNjRotation()`; a first-time line backfills from `2000-01-01`). Picking CC adds an optional file field for the monthly schedule. Skip leaves it for My Info, and a pilot with no rotation has no tour days. `njLineToAnchorDate()` must match `_lineToAnchorDate()` in app.html. The admin panel and My Info use the same label.

**Beta reset endpoints** (admin-or-self): `DELETE /api/pilots/:key/tour-tail` (one tour), `DELETE .../cc-schedule` (one month), `DELETE .../rotation` (rotation + seams + CC variant, falls back to pure segment-based off days). Each finalizes any open auto-created leg under the cleared tail first.

**Tour reminder, two layers.** `checkNetjetsTourReminders()` (server.js, every 6h) sends a push/in-app notification the evening before each tour's Day 1 if no tail is saved, deduped via `pilot_tour_reminder_sent`. `_maybeShowNetjetsTailReminder()` (client, called from `loadPilot()`) shows a modal once per day, localStorage-deduped, on the evening before Day 1 and on Day 1 itself; its button opens the tour modal.

**Admin edits a pilot's tour from the day-detail sheet.** Viewing the pilot's schedule as admin shows the same Edit Tour button. `#edit-user-netjets-section` in the admin panel (`_loadEditUserNetjetsStatus()`) stays read-only, and rotation and CC schedule are still self-service in the app.

**Line-switch seam transition.** `scripts/build-seam-tables.js` → `public/seam-tables.json` (14 `7Line*` keys, `8Line2/4/6/9/11/13` only for 8&6 — a property of the seam table's own data coverage, not a restriction on which lines are generally valid elsewhere). When `saveMyRotation()` detects a real family/line switch, `PUT /:pilotKey/rotation` computes a 28-day override window (`_computeSeamWindow()`) stored in `pilot_duty_rotation_seam(window_start_date, from_key, to_key, table_letter)`, returned as `rotation_seams`. `_seamOverrideFor()` looks up the per-day value inside a stored window; falls through to the normal rotation formula otherwise. Family/Line pickers default to a blank placeholder so a save can't silently lock in the wrong line by omission.

**CC schedule override (CC52/60/72/76).** For pilots who bid per-trimester totals with no repeating cadence — their schedule can only come from a real NetJets Yahoo Mail monthly export. `parseCcScheduleText()` parses one line per day (`<DayAbbr>, <MonAbbr> <DD>, <YYYY> <STATUS>`; `X`=duty, `OFF`=day off, `P<n>`=PTO), warning (not erroring) on anything unrecognized. The email's `Date:` header and "subject to change" footer are skipped without a warning. Stored in `pilot_cc_schedule_day` (`UNIQUE(pilot_id, date)`), returned as `cc_schedule_days`. **Intake is the standard Upload button only** — `POST /:pilotKey/upload` special-cases `parser_type==='manual_netjets'` before the normal dispatch, accepting a `.txt` or `.pdf`. Response shape: `{success, ccSchedule:true, daysParsed, warnings}`.

**PDF support uses real OCR** (`_ocrPdfBuffer()`): `pdftoppm -png -r 200` (poppler) rasterizes each page, then the **native `tesseract` CLI** (not the `tesseract.js` npm package — see history for why) OCRs each page image. Both are system packages (`apt-get install poppler-utils tesseract-ocr`) — check `which pdftoppm tesseract` first if PDF upload breaks on a fresh droplet. Both calls carry a 60s timeout/SIGKILL backstop. Real-world latency on the live droplet (sharing one vCPU with SWIM/STDDS/ADS-B pollers) is ~53s for a typical schedule PDF — `handleUpload()`/`handleMobileUpload()` show an upfront "this can take up to a minute…" toast for `.pdf` uploads specifically.

**Surfaced as a third option on the Duty Rotation Family dropdown** (`7 & 7` / `8 & 6` / `CC (52/60/72/76)`), not a separate section — picking `CC` hides the Line picker/Save button and shows a plain note pointing at Upload instead. `openEditMyInfoModal()` defaults to `CC` whenever `cc_schedule_days` has any rows, even if a stale rotation row exists underneath.

**Where a NetJets pilot is (Crossings, here-now, calendar away days).** The airline rules don't fit, so they're adjusted for `manual_netjets` only:
- **Auto-commute home** (`_netjetsHomeWindows()`): NetJets pilots airline home on a tour's last day and rarely log it. From 3h after the last leg lands on that day (same 3h rule as an airline commuter landing at base; midnight if that day has no legs) through the end of the off-duty run, they're at `home_airport`. Applied in Crossings (`_netjetsHomeOnOffDays()`, which emits periods flagged `absolute` so `adjustedPeriod()` leaves them alone), both here-now pins (`_netjetsOffDutyHome()`, step 4b in `renderDayMap()`), and `inferAwayLayovers()` (no away days on off-duty days). No rotation/CC configured means no change.
- **Filing horizon**: an open-ended away stay (no later leg departs it) is cut at `max(now, arrival) + 18h`. Up to now it's backed by tracking, since the tail is watched all tour. Beyond about 18h NetJets hasn't filed yet, so the location is unknown, not "still at the last airport".
- **Voluntary tour extension**: "＋ Extend 1 day" / Undo in the tour modal (`extendNetjetsTour()`/`unextendNetjetsTour()`) adds or removes the day after the tour's current last day in `pilot_tour_extension(pilot_id, date, tour_start_date)` (`UNIQUE(pilot_id, date)`, returned as `tour_extensions`; `PUT`/`DELETE /api/pilots/:key/tour-extension`, admin-or-self). It's keyed to the tour it extends, so the tour start and saved tail don't change, unlike a CC `X` record. It has the highest precedence in `_isNetJetsOnDuty()`, `_tourStartDateFor()` (`_tourExtensionFor()`) and server `_netjetsTourStartServer()`, so tracking, Off Days, the calendar and the auto-commute all move to the new last day. `_tourEndDateFor()` walks the real tour for the modal's range text instead of assuming `days_on`.
- The server's `GET /api/pilots/:key/here-now` debug reimplementation does **not** have these rules.

**Crossing pushes on app open**: the background `computeOverlap()` at startup also calls `broadcastCrossingNotifications(overlaps, 48h)`, so legs that appear on their own (NetJets legs filed the evening before, server-side ICS/Schedaero syncs) still alert both pilots the next time either opens the app. Only pairs involving the signed-in pilot are sent, and the server dedupes per crossing. **Tour UX**: the no-tail reminder fires on any tour day without a tail (once a day), and future tour days with no legs show "Legs show up once NetJets files them — usually the evening before."

**Resolution precedence, `_isNetJetsOnDuty()`**: (1) `_ccScheduleOverrideFor()` — explicit CC day record, if one exists; (2) `_seamOverrideFor()` — seam transition window; (3) fallback to the normal rotation formula. A pilot's CC schedule overrides any overlapping tours from a previous 7&7/8&6 schedule, by design.

**Switching onto CC ends the formula.** Saving CC (`PUT /rotation` with `ccVariant` + `effectiveFrom`) inserts a `days_on=0` row dated today. Both `_resolveRotationAt()`/`_resolveRotationAtServer()` treat that row as "no rotation" from then on (`_resolveRotationRowAt()` returns it raw, and `_seamOverrideFor()` stops applying past it), so days without uploaded CC data are off, not 8&6. History before the switch is untouched. Saving a 7&7/8&6 line again clears `cc_variant` and adds a dated row; any existing history means a dated change, never the `2000-01-01` backfill.

**Tour start is CC-aware** (`_tourStartDateFor()` client, `_netjetsTourStartServer()` server, used by `_getOnDutyNetjetsPilots()` and `checkNetjetsTourReminders()`): a CC day record wins. A CC tour is a run of consecutive `X` days, starting at its first `X` (spans month boundaries). With no record for that date, it uses the rotation formula. **A CC pilot with no uploaded month is off-duty, so their tail isn't tracked.**

**Clear Month** (`#my-info-cc-clear-month`) is a `<select>` of months that actually have uploaded CC days, latest preselected (`_refreshCcClearMonthOptions()`).

**Known blind spot**: getting to/from the jet on day 1 / the last day of a tour is typically a commercial deadhead, invisible to tail-based tracking. The manual "Commute" flight type (`trip='COMMUTE'`) is the fallback, surfaced via the tour modal's commute shortcut above.

**Airport display**: NetJets legs always show 3 letters. A code like `KSDL`, `KCQF` or `KBKV` keeps its K in the data because the bare code is another airport (Sundsvall, Calais, China), and `resolveAirport()` tries the bare code first. `aptLabel(code, pilotKey)` drops the K for `manual_netjets` pilots at display only, so **never pass its result to a lookup** (`resolveAirport()`, `tzAbbr()`, `formatTimeISO()`, `flightUTCTime()`, `_intelAreaLabel()`). With no pilot (Crossings, shared map labels) it drops only a K kept for a collision. Other pilots are unchanged, so Kyle's `KSUS` stays. Add Flight and edits run a NetJets work leg through `norm3Airport()`, so a typed `CQF` is stored as `KCQF`. Personal and commute flights are airline tickets with real IATA codes, so they're stored as typed. The Lookup page shows stored codes, for comparing with FlightAware.

**Tail display**: a pilot enters just the tail digits ("742"); `displayTail()` shows the full `N742QS` wherever a reader sees it, without changing what's stored.

**`/crew-roster/netjets-lookup`** — one page per tail covering both `EJA####` and `N####QS` (tail list grouped by tail, Callsign column in Filed, FlightAware links for both). Fleet-wide validation tool over `tfdm.getAllLegs()`/`tfms.getAllLegTimes()`. With no tail, it lists every research-mode callsign with captured data (`getCallsignsWithLegs()`/`getCallsignsWithLegTimes()`). `?tail=` accepts digits or a literal `N####QS`. Per tail and date range it shows:
- **Filed** — raw candidates.
- **Resolved** — `resolveNetjetsLegsForDisplay()`, a read-only simulation of the leg-creation filter, never writes to the DB. It picks the most recently updated TFMS entry for the same origin/departure instant (not TFDM's possibly stale dest), propagates confirmation backward through the chain (a leg that the next confirmed leg chains onto must have flown), and drops unconfirmed candidates departing from an airport the tail was never confirmed at. A **Confirmed?** column reads green once TFDM shows real movement, red when 3h past departure with none, grey while upcoming.

- **On the pilot's schedule** — only for a tail a CrewSync pilot saved in `pilot_tour_tail`: the segments actually created (auto, edited, or manual; flown/scheduled/hidden). This is the real result to compare with Resolved and FlightAware. Those tails are labeled with the pilot's first name in the tail list.

Kyle uses this page to compare each tail against FlightAware, so times show in local airport time with a TZ abbreviation (UTC underneath), rows are grouped by local day, and Filed has an **Evidence** column (TFMS dep/arr/radar, TFDM movement). Timezones use `_lookupTzForAirport()`: by coordinates (US `K`-code preferred for a 3-letter code, since the bare IATA table collides, e.g. BKV resolved to GMT+8), nearest airport with a known zone. That also covers small fields like E38/27K. Pilot-edited rows (local time, no `Z`) are converted to UTC before display, and every table sorts by the time it shows. The handler is `async` (DB reads for pilot tails and segments).
